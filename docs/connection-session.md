# 연결 세션 확인 및 서버 복구

## 목적과 범위

NearLink끼리 GATT 서버 세대와 읽기·알림 구독 준비 상태를 확인한다. 삼성 시스템의 배터리 프로필과 위젯은 이 절차에 참여하지 않는다. 앱의 연결 완료는 삼성 목록이나 실제 위젯 갱신을 보장하지 않는다.

## 연결 순서

1. 기존 암호화 제어 특성 `734b7301-53b1-4cf0-8d2e-d4b5c742b65b`에 JOIN(1)을 보내 기존 등록·준비 시간 및 선택 기기 검증을 수행한다.
2. 새 암호화 읽기/쓰기 특성 `734b7302-53b1-4cf0-8d2e-d4b5c742b65b`가 있으면 HELLO를 쓴다. 클라이언트는 탐색마다 새 요청 ID를 만든다.
3. 같은 특성에서 READY를 읽고 요청 ID와 서버 세션 ID를 확인한다. 서버 세션 ID는 GATT 서버를 열 때마다 새로 생성하며 프로세스 로컬 generation 로그 번호와 다르다.
4. Battery Level과 Battery Level Status를 읽고 두 특성의 CCCD 구독 설정 응답을 기다린다.
5. 동일 요청 ID·서버 세션 ID를 담은 ACK를 쓴다. 서버는 현재 선택된 페어링 기기인지와 두 CCCD가 설정되었는지 검사한다. 성공하면 최신 배터리 알림을 전송한다.
6. 클라이언트는 ACK 쓰기 성공 및 ACK 전송 시작 이후의 유효한 Battery Level 알림을 모두 확인해야 CONNECTED로 전환한다. 알림과 쓰기 콜백의 도착 순서는 바뀌어도 된다. 준비 중 읽은 값은 마지막 수신 기록으로 저장하되 연결 완료로 표시하지 않는다.

모든 GATT 작업은 기존 큐에서 직렬 실행된다. 개별 요청 및 ACK 이후 알림 대기는 20초가 지나면 실패 처리하고 재연결한다. 준비 완료 전 서버 측 pending 요청 역시 20초만 유효하다. 완료된 세션은 30초 heartbeat 간격 때문에 만료되지 않는다. 연결 해제 시 해당 기기 상태를 삭제한다.

CONNECTED 이후 약 30초마다 기존 JOIN 유지 확인과 SESSION 읽기를 수행한다. 요청/서버 세션 불일치, 읽기 실패, 서비스 변경은 앱의 재탐색·재연결 및 새 handshake로 복구한다. 응답에는 비밀 키를 담지 않으며, ID는 새 연결과 지연 응답을 구분하는 용도다. 인증은 기존 암호화·bond·선택 기기 검증에 의존한다.

## 패킷

모든 정수는 little endian이며 최소 ATT payload인 20바이트 이내다.

| 메시지 | 형식 | 길이 |
| --- | --- | --- |
| HELLO | 버전 1(1바이트), 종류 1(1바이트), 요청 ID(8바이트) | 10 |
| READY | 버전 1, 종류 2, 요청 ID(8), 서버 세션 ID(8) | 18 |
| ACK | 버전 1, 종류 3, 요청 ID(8), 서버 세션 ID(8) | 18 |

형식·길이·버전이 다르거나 ID가 0이면 거부한다. ACK는 요청과 서버 세대가 모두 일치해야 한다. 중복 ACK는 같은 세션에 대해 안전하며 최신 알림을 다시 보낸다. SESSION 특성이 없는 구버전 또는 표준 BAS 기기는 기존 읽기·구독 큐를 사용하며 로그에 `sessionVerified=false`로 구분한다. 새 프로토콜 특성이 있는데 실패한 경우 구버전 경로로 조용히 우회하지 않는다.

## 알림 전송 복구

- busy 또는 실패 응답은 최신 값을 합쳐 1, 2, 4, 8, 16, 최대 30초 간격으로 재시도한다. 성공 시 백오프를 초기화한다.
- 전송이 수락됐는데 콜백이 늦으면 같은 전송이 진행 중인 상태를 유지한다. 이전 콜백이 새 전송으로 잘못 해석되지 않도록 다른 전송을 겹쳐 보내지 않는다.
- 15초, 30초, 60초 시점의 세 번 연속 콜백 시간 초과 후에만 서버를 재생성한다. 첫 시간 초과에서 즉시 서비스를 제거하지 않는다.
- 서버가 이미 열려 있으면 startBle는 중복 생성하지 않는다.

서버를 실제로 재생성하거나 다른 앱이 GATT 구성을 변경할 때 삼성 시스템의 기존 배터리 프로필이 남아 값이 멈출 수 있다. 다음 복구 절차는 해당 상태를 완화하지만 모든 기기의 자동 복구를 보장하지 않는다.

## 서비스 변경 후 배터리 프로필 복구

- 연결이 준비된 뒤 상대 기기의 서비스 변경이 감지되면 NearLink는 자체 서비스를 다시 검색하고 세션과 구독을 복구한다. 그 후 현재 선택된 페어링 기기에 암호화 제어 명령 3을 보내 양쪽 수신 연결을 잠시 정리한다. 다른 기기와의 연결을 직접 끊거나 Bluetooth 전체를 끄지는 않는다.
- 상대 기기가 명령을 수락하면 양쪽 수신기는 15초간 연결을 중단하고 다시 연결한다. 이 기간에 앱에서 서비스를 다시 시작하더라도 중단이 유지된다. 서비스 변경이 연속해서 발생하면 복구 시도는 기기별로 10분 이상 간격을 두고, 제한 시간 안에 발생한 변경은 연결이 유지되는 동안 대기시켰다가 다시 시도한다. 구버전 기기가 명령을 거부하면 기존 연결을 유지한다.
- 검색 후에도 광고를 찾지 못하면 저장된 페어링 기기에 직접 연결을 시도하고, 실패하면 기존 백오프로 재시도한다. 초기 두 번의 검색은 빠른 검색을 사용한다.
- 실제 BLE 링크가 내려가는지는 두 기기의 다른 연결과 Bluetooth 스택에 달려 있다. 삼성 시스템의 재구독이나 위젯 화면 갱신을 직접 제어하거나 확인하는 기능은 아니므로 완전한 복구를 보장하지 않는다. 양쪽 기기에 이 변경이 설치되어야 협조 복구가 가능하다.

## 2026-11-10 검증 결과

- `assembleDebug`, `testDebugUnitTest`, `lintDebug` 성공. 단위 테스트 총 23개 통과. 세션 ID/버전/길이 검증, 오래된 요청/서버/기기 ACK 거부, 준비 만료, 구독 전 ACK 거부, ACK 쓰기/알림의 역순 도착 및 재시도 예산을 검증했다.
- SM-S936N과 SM-X730에 수정 Debug APK를 설치했다. 새 폰과 구버전 태블릿의 양방향 기존 프로토콜 수신을 먼저 확인했다.
- 양쪽 수정본 설치 후 HELLO/READY/ACK와 실제 알림 수신을 완료하고 두 방향 모두 `stream ready sessionVerified=true`를 기록했다. 이후 SESSION heartbeat 읽기도 성공했다.
- 폰 BatteryService만 중지/재시작한 1회 시험에서 태블릿이 서비스 변경·BAS 소멸을 감지하고 재연결 후 새 서버 세션으로 handshake를 완료했다. 이 시험에서는 실제 ACL도 재연결되어 삼성 목록이 재등록됐다.
- 서버 재생성 이후 자연 방전 42→41%, 시험값 40%, reset 후 실제 41%를 앱과 삼성 시스템 목록 모두에서 확인했다. 시험용 battery override는 finally에서 해제했다.
- 반복 서비스 시작 요청 2회에서 추가 GATT 서버 생성이 없는 것을 확인했다.
- 최종 폰 실측 41%, 태블릿 앱 저장값 41%, 삼성 시스템 변경 기록 41%. 삼성 위젯 화면 자체는 직접 확인하지 않았다.
- 콜백 유실/60초 서버 재생성 정책은 단위 테스트로 확인했으며 실제 기기에서 콜백을 강제로 유실시키지는 않았다. 서버 교체 후 삼성 연결이 계속 남는 모든 조건의 자동 복구, 장시간 절전과 재부팅은 검증되지 않았다.

## 2026-11-11 장시간 실행 중 위젯 갱신 중단

- 사용자는 태블릿의 삼성 배터리 위젯이 폰 잔량을 48%로 계속 표시한다고 보고했다. 위젯 화면의 48%는 직접 확인하지 않았다.
- 확인 시 폰의 실제 잔량은 93%였고 태블릿 NearLink는 94→93% 알림을 정상 수신했다. 폰의 알림 전송 콜백도 성공했다. 이는 삼성 시스템의 알림 수신이나 위젯 갱신을 보장하지 않는다.
- 태블릿의 삼성 Bluetooth BatteryService는 전날 22:07부터 `Connected` 상태였지만, 시스템 `android.bluetooth.device.action.BATTERY_LEVEL_CHANGED` 방송 기록은 23:06:23 이후 확인되지 않았다. 이 방송 기록만으로 마지막 값이나 대상 기기를 확정할 수는 없다.
- 폰에서 23:06:27에 Google Play 서비스의 Nearby Connections GATT 서버가 종료되고 다시 등록되면서 Service Changed indication이 발생했다. 태블릿의 삼성 BatteryService 연결은 23:06:30에 이를 수신하고 서비스 검색을 다시 수행했다. 시간상 갱신 중단과 인접하지만 이것이 원인이라는 인과관계는 아직 검증하지 못했다. NearLink GATT 서버가 재생성된 것은 아니다.
- 현재 확인된 문제는 NearLink의 세션 handshake 성공만으로 삼성 시스템의 별도 배터리 프로필이 계속 갱신된다고 판단할 수 없다는 점이다. 삼성 프로필의 재구독 상태와 위젯 화면을 포함한 재현 및 복구 방법은 추가 검증이 필요하다.

### 추가 원인 분석

- 태블릿(Android 17, One UI 9)에는 삼성 시스템 BatteryService와 NearLink가 각각 별도의 GATT 클라이언트로 등록되어 있었다. 한 클라이언트의 정상 수신은 다른 클라이언트의 알림 등록 상태를 뜻하지 않는다.
- 공개 Android Bluetooth 구현의 한 버전에서는 Service Changed의 영향 범위에 속한 기존 알림 등록을 지운다. [GATT 구현](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/aml_ads_341826060/system/bta/gatt/bta_gattc_act.cc)에서 `bta_gattc_clear_notif_registration`을 호출하는 경로를 확인할 수 있다.
- 공개 Android BatteryStateMachine의 한 버전은 연결 직후 서비스 검색과 배터리 알림 등록을 하지만 `onServiceChanged` 재등록 처리를 구현하지 않는다. 반면 NearLink는 서비스 변경 시 재검색과 알림 등록을 수행한다. [BatteryStateMachine 구현](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/7391423f063c2e5639fefae102b4ff7d0816508e/android/app/src/com/android/bluetooth/bas/BatteryStateMachine.java)
- 따라서 Nearby의 서비스 변경이 삼성 시스템 클라이언트의 알림 등록을 무효화하고 복원하지 못했을 가능성이 있다. 이는 공개 구현과 관측된 시간 순서에 근거한 가설이다. 삼성 기기에 적용된 실제 코드, 변경된 핸들 범위, 해당 클라이언트의 등록 해제·재등록 여부는 확인하지 못했으며 마지막 시스템 방송도 기기와 값을 식별하지 못했다. 위젯이 48%로 고정된 정확한 경로는 아직 확정할 수 없다.

### 복구 실기기 시험

- SM-S936N과 SM-X730에 복구 로직이 포함된 디버그 빌드를 설치하고, 폰에 임시 GATT 서비스를 추가·제거해 서비스 변경을 재현했다. 자동 복구 명령 수락 후 두 NearLink 수신기가 일시 중지되고 태블릿에서 실제 ACL 해제와 삼성 BatteryService의 종료가 기록됐다.
- 이후 두 앱이 자동 재연결했고 태블릿의 삼성 BatteryService도 다시 연결됐다. 스마트폰 실제 잔량 91%를 태블릿 앱과 삼성 시스템이 기록했으며, 시험용 90%로 변경했을 때도 양쪽이 90%를 수신했다. 배터리 시험값은 즉시 reset했고 임시 진단 앱도 제거했다.
- 지연 복구를 추가한 최종 디버그 빌드에서도 임시 서비스 추가·제거 후 두 앱이 복구를 수행해 자동으로 다시 연결됐고, 당시 스마트폰 실제 잔량 90%를 태블릿의 삼성 BatteryService와 NearLink에서 확인했다. 반복 요청 제한 시간 계산은 단위 테스트로 확인했으며 10분 경과 후 자동 재시도는 실기기에서 기다려 검증하지 않았다.
- 위젯 화면 자체와 장시간 동작, 다른 앱이 같은 기기에 연결을 유지하는 경우는 확인하지 못했다. 시험은 복구 시도 중 다른 연결이 BLE 링크를 유지하지 않는 조건에서 수행했다.
